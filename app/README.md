# ER/MDM Studio — Phase 1(ローカル版)

名寄せ(Entity Resolution)とマスターデータ管理のアプリケーション。**使い方は [ユーザーズガイド](../users-guide/README.md) を読んでください**(この文書は開発者向けの概要です)。要求は [`work/prd.md`](../work/prd.md) の Phase 1 に対応します。

- **Python 標準ライブラリのみ**(外部パッケージ不要、Python 3.12 で検証。3.10 以上を想定(未検証))。SQLite に保存し、`127.0.0.1` だけで待ち受けます。
- 画面は d3.js v7(`web/vendor/` に同梱。ネットワーク不要)。
- **組織外へ通信しません**(テストで確認)。

## 起動

```powershell
cd app
python -m ermdm serve --data .\data --port 8800 --admin-password <管理者のパスワード>
# ブラウザで http://127.0.0.1:8800/ を開く(ユーザー名 admin)
```

- `--admin-password` を省くと、初回起動時に乱数のパスワードを一度だけ表示します。
- `--demo-users` は役割ごとのデモユーザー(`steward` / `demo-steward-pass` など)を作ります。**ローカル検証専用**。実運用では使わないでください。
- 体験用データ: ダッシュボードの「人物デモ(1,000件)」「企業デモ(4ソース)」(合成データ。`sample_data/`)。CLI なら `python -m ermdm demo persons --data .\data`。
- `--data` 配下の `import/` に置いた CSV / SQLite は、API から `import_path` で取り込めます(それ以外のパスは読めません)。

## 使い方の流れ

1. **ソース**: CSV を貼り付け/選択して取り込む。個人データなら「個人データを含む」と**利用目的**を紐づける(無いと実行できません)。
2. **設定**: 同一性の定義とコスト比 → 標準化 → ブロッキング(候補数の事前見積) → モデルの学習 → 閾値。
3. **実行**: 実行すると、候補ペア → 確率 → クラスタ → グローバルID → 確認キューが作られ、結果ハッシュが記録されます。
4. **エンティティ / 確認キュー**: 根拠を見て、判定(理由必須)や分割ができます。判定・分割は制約として残り、再実行でも覆りません。
5. **評価 / ラベル付け**: 正解付きなら閾値曲線(ペア・クラスタ別)とコスト最適、無ければ層化サンプルに盲検でラベルを付けて推定します。
6. **ガバナンス / タスク**: 利用目的、役割、改ざん検知つき監査ログ。PRD のタスク表の取り込みと依存(DAG)管理。

## テスト

```powershell
cd app
python -W ignore -m unittest discover -s tests      # 61 件(約 8 秒)
python -m ermdm coverage                            # docs/requirements_coverage.json を生成
python -m ermdm verify --data .\data                # 監査ログの連鎖を検証
```

テストの docstring に `[FR-xxx-nn]` を付け、PRD の Phase 1 の要求との対応を `docs/requirements_coverage.json` に出します。

## 限界(必ず読んでください)

- **Phase 0 のゲートは未了です。** 閾値(自動 0.9 / 下限 0.5)とコスト比(5)は**仮の既定値**で、ダッシュボードに未決事項として表示されます。同一性の定義・コスト比は業務側の承認が必要です。
- 検証はすべて**合成データ**(`sample_data/`)です。実データでの精度・閾値は未測定です。
- 純 Python の実装です。規模の目安は未測定で、候補ペア数の上限(既定 200 万)を超えると実行前に停止します。大規模には Splink / DuckDB 等への差し替えが必要です(マッチャは `matching.register_matcher` で差し替え可能)。
- **含まないもの(Phase 2 以降)**: PLM / LLM マッチャ、kNN ブロッキング、法人番号・町字ID の外部参照、承認ワークフロー、有効期間つきの同一性、サバイバーシップ、モニタリング、ドリフト検出。
- 一部は Phase 2 の要求を最小限だけ先に実装しています(否定制約 FR-CLU-04 の永続化など)。
- 画面の要求 FR-VIZ-01〜03、NFR-11/12 は**ブラウザでの手動確認**のみで、自動テストはありません(`docs/requirements_coverage.json` の `manual`)。FR-VIZ-03 の閾値スライダーと橋渡し/最弱リンクの強調は未実装です。
- 認証は単一マシン向けの簡易なもの(PBKDF2 のパスワード、HttpOnly Cookie)です。ネットワークに公開しないでください(`127.0.0.1` 以外では待ち受けません)。
- 個人番号(マイナンバー)は、列名・12桁のチェックデジットで検出して取り込み時に**隔離**します。検出は完全ではないため、取り込み前の除外も併用してください。
