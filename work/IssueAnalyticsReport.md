## 0. 依頼の再設計(実行前の提示)

### (1) トップ専門家が、頼まれなくてもやること
1. 「名寄せ」を1問題とみなさず分解する: 標準化 → ブロッキング(候補生成) → ペア判定 → クラスタリング → 統合(サバイバーシップ) → 運用(分割/アンマージ、履歴、ガバナンス)。
2. 誤統合(false merge)と誤分割(false split)のコスト非対称性を業務ごとに定義する。
3. 精度を「単一の正解率」で語らない。ペア指標・クラスタ指標・自動化率・信頼区間を分けて見る。
4. 「IDが違う」のか「意味が違う」のか「同一性の定義が違う」のかを切り分ける(下記3章)。
5. 大企業固有の連携方式(ファイル連携/DB同期/CDC)ごとの失敗モードを洗い出す。
6. 自分の主張が弱い部分(一次資料で未確認の部分)を明示する。

## 1. 問題の定義と用語

| 用語 | 意味 |
|---|---|
| Entity Resolution (ER) | 複数の記述が同一の実世界エンティティを指すかを判定し、まとめる処理。Entity Matching は「2記述が同一か」のペア判定段階を指すことが多い |
| Record Linkage | 主に統計/公的データ分野の呼称。複数データセット間の紐付け |
| Deduplication | 単一データセット内の重複排除 |
| MDM | マスタデータを一元管理する運用・ガバナンス。ER はその中核技術 |
| 名寄せ | 日本の実務用語。顧客/取引先などを同一主体としてまとめること(ER+統合を含めて使われることが多い) |

Peeters ほか(arXiv:2310.11244)は、Entity Matching を「2つのエンティティ記述が同じ実世界エンティティを指すかを決めるタスクで、多くのデータ統合パイプラインの中心ステップ」と定義している(確認済み)。

## 2. 大企業システムで問題が起きる構造

業務連携をファイル共有やDB同期で行うと、次の要因が重なる(以下は一般的なエンジニアリング知見に基づく整理であり、特定の論文の結論ではない。自社での確認が必要)。

1. **共通キーが存在しない/信頼できない**: システムごとに採番(顧客番号、取引先コード)。キーの再利用、共有、欠損、誤入力がある。
2. **意味の不一致(セマンティクス)**: 「顧客」が契約者か利用者か、「売上日」が受注日か請求日か。同じ列名でも意味が違う。
3. **同一性の粒度の違い**: 法人/事業所/部署、個人/世帯、商品/SKU/型番のどのレベルで同一とみなすか。
4. **表記ゆれ**: 全角半角、旧字体、略称、(株)と株式会社、住所表記、カナ/ローマ字。
5. **時間変化**: 社名変更、移転、合併。「変化した同一主体」と「別の重複」の区別。
6. **同期の遅延と不整合**: バッチ/ファイル連携でのタイミング差、DB同期(CDC等)での更新競合、削除の伝播漏れ。
7. **統合後の逆戻り困難**: 誤統合された後で、下流システムに伝播したIDを分割することが難しい。アンマージは一級要件にすべき。

## 3. 切り分けフレーム(最初に決めること)

| 症状 | 真因の候補 | 対処の方向 |
|---|---|---|
| 同じ顧客に複数IDがある | キー不在、システム別採番 | クロスリファレンス表、グローバルID(ER結果のクラスタID) |
| 同じIDなのに別物 | キー再利用/誤入力 | キーを証拠の1つとして扱い、絶対視しない |
| 項目の値が合わない | 意味・単位・粒度の違い | データ辞書、標準化、契約(data contract) |
| 昔は一致、今は不一致 | 時間変化 | 履歴(有効期間)付きの同一性管理 |

## 4. 技術パイプラインと代表手法

### 4.1 前処理・標準化
Splink公式ドキュメントは、入力データを事前に標準化(小文字化、記号除去、列名統一など)すべきで、相関の低い複数列があるデータで最も性能が出ると述べている(確認済み: moj-analytical-services.github.io/splink)。

### 4.2 ブロッキング/フィルタリング(候補ペア生成)
全ペア比較は O(n²) で非現実的。Papadakis ほかのサーベイ(arXiv:1905.06167)は、効率化技術をブロッキング・フィルタリング・ハイブリッドに整理し、半構造化ビッグデータでは「ブロッキングにスキーマ知識が要る」「フィルタリングに高い類似度閾値が要る」という前提が崩れるため、スキーマ非依存ブロッキングやより緩い類似基準が導入されたと述べる(確認済み)。VLDB Journal 2024 にもフィルタリング技術のオープンベンチマークがある(検索結果で存在確認、本文は未精読)。

**失敗モード**: ブロックが粗すぎて計算量爆発/細かすぎて真の一致を取り逃がす(再現率の天井になる)。

### 4.3 ペア判定
- **確率モデル(Fellegi–Sunter)**: Splink の中核アルゴリズムと明記されている(確認済み)。教師なし学習(EM)でも訓練可能。1M件を約1分(ノートPC)、Sparkで1億件超という公式主張あり(ベンダー/作者主張。条件依存で未検証)。
- **PLM(Ditto)**: エンティティ対を系列ペア分類としてファインチューニング。ベンチマークで従来SOTAを最大29% F1上回り、2つの企業データ(789K件と412K件)でF1 96.5%(確認済み: arXiv:2004.00584)。ただし大量の訓練データを要する。
- **LLM**: Peeters ほかは、最良のLLMは少数または無訓練例でも、数千例で微調整したPLMに匹敵する性能を示し、未知のエンティティに対してより頑健であること、ただし「最良のプロンプトはモデル/データセットの組み合わせごとに調整が必要」と報告(確認済み: arXiv:2310.11244)。コスト・遅延・再現性(プロンプト感度)が運用上の論点。
- **埋め込み**: Zeakis ほか(arXiv:2304.12329)は、12の言語モデルを17の既存ベンチマークで、ベクトル化コスト、ブロッキング性能、教師あり/教師なしマッチングの観点から評価(確認済み)。モデル選択は経験的に行うべきという示唆。

### 4.4 クラスタリングと推移閉包の危険
ペア判定結果を「エンティティ」にする工程は別設計。連結成分(Splinkの既定)では A=B, B=C なら A と C が直接否定されていても同一クラスタになる(二次情報: Architect Knowledge Library がSplinkの記述を引用、一次資料での再確認が望ましい)。結果として「1人の顧客に別人3名」という本番障害が起こりうる。

### 4.5 統合(サバイバーシップ)と運用
どの値を「正」とするか(最新、信頼度の高いシステム優先、など)のルール、人手レビュー(スチュワードシップ)キュー、アンマージ、監査ログ。これは技術というより運用設計であり、論文より実務書/ベンダー資料が主な情報源(一次評価は困難)。

## 5. 評価の落とし穴(第三者検証のため)

- 全ペアの大半が非一致なので、**単純なAccuracyは無意味**(全部「非一致」と答えても高得点)。Precision/Recall/F1(ペア)に加え、クラスタ指標、**自動確定分のPrecisionと自動化率**を併記する(二次情報: Entity Bind のガイド。ベンダー記事であり、論旨は一般的な評価論と整合するが一次ではない)。
- **誤統合と誤分割のコストは非対称**: 例)支払先マスタでは誤統合が重大、マーケ重複排除では誤分割が許容されやすい。閾値は業務損失で決める。
- ベンチマーク性能は自社データへ一般化しない。Peeters らは、微調整PLMは分布外エンティティに頑健でないと指摘(確認済み)。
- ラベル付きサンプルは必須(複数人で付与し一致度を測る)。信頼区間とサンプルサイズを明記する。

## 6. 大企業向けベストプラクティス(統合的整理)

以下は、上記の確認済み知見+一般的な設計原則に基づく推奨で、特定の単一文献の結論ではない。

1. 先に**同一性の定義**(粒度・時間)と**誤りコスト**を業務と合意する。
2. 既存の共通キーは**証拠の1つ**として使い、決定的ルール(法人番号等の信頼できるキー)+確率的照合の**ハイブリッド**にする。
3. 段階導入: 標準化 → 決定的ルール → ブロッキング+確率モデル(Splink等で説明可能なベースライン) → 必要箇所のみPLM/LLM。LLMは「グレーゾーン」の再判定に限定するとコストを抑えやすい(設計提案。検証が必要)。
4. 結果は**クロスリファレンス表(ソースID↔グローバルID)**として保持し、元データを破壊的に書き換えない。統合は可逆(アンマージ可能)に。
5. 連携面: ファイル連携/DB同期ではスキーマ・意味の**データ契約**とバージョン管理、冪等な再取り込み、削除/更新の伝播規約を定める。
6. モニタリング: 一致率、レビューキュー量、定期的な再ラベルによる精度のドリフト検出。
7. 個人情報: 名寄せは個人データの結合となるため、法令(個人情報保護法/GDPR等)の利用目的・同意範囲の確認が必要(法務確認事項。本調査では詳細未調査)。

## 6B. 日本固有の事情と公的基盤

### 6B-1. 法人番号(国税庁)
- 法人番号は**13桁**で、**利用範囲の制約がなく誰でも自由に利用できる**(国税庁「法人番号とは」)。
- 公表される基本3情報は、商号又は名称、本店又は主たる事務所の所在地、法人番号。そのほか、名称のフリガナ(法務局でフリガナを記載して登記申請等をした場合のみ)、英語表記(登録した場合のみ)、名称・所在地の**変更履歴**など(確認済み)。
- 設立登記法人以外(人格のない社団等)は、代表者等が公表に同意した場合のみ公表される(確認済み)。
- Web-API(REST)で、法人番号指定、取得期間指定(最大50日)、法人名指定の取得ができる。**Web-APIでは全件データは取得できない**(全件はダウンロード機能を使う)。アプリケーションID発行には2週間〜1か月程度かかる(確認済み: 法人番号公表サイトWeb-API案内)。
- **名寄せ上の意味**: 取引先マスタに法人番号を付与できれば、強力な決定的キー(ブロッキング・照合の根拠)になる。変更履歴は「社名変更した同一法人」の同定に有用。**限界**: 個人事業主や、番号が付かない主体には使えない。法人番号は事業所(支店・工場)の粒度を持たない(法人単位であり、事業所単位の同定は別途必要。一般的な整理で、公式ページで事業所番号が存在しないことの確認までは未実施)。

### 6B-2. 住所(アドレス・ベース・レジストリ)
- デジタル庁は、住所・所在地について、制度が不動産登記法と住居表示法に分かれ、行政が一元的に管理していないという構造的課題を挙げている。その結果、民間が個別に整備して**表記揺れが生じやすく、システム間のデータ連携・統合が困難**になっていると明記(確認済み: デジタル庁)。
- 2025年6月に町字データを正式版として公開。町字IDは、自治体の基幹業務システムの標準仕様の「住所_町字コード」で使うものと規定。**現時点で整備済みなのは町字(文字情報)までで**、地番・住居表示等は検討中(確認済み)。
- **名寄せ上の意味**: 町字IDで住所を都道府県〜町字まで正規化できるが、番地・号・建物名まではカバーされないため、残りは自前の正規化・照合が必要。

### 6B-3. 日本語特有の表記揺れ
- 住所の表記揺れ・異体字は、研究コミュニティでも対象となっている(例: ROIS-DS CODH が公開する日本の住所ジオコーダ jageocoder を拡張した歴史的ジオコーダの開発事例で、表記揺れ・異体字への対応を扱っている。ただし現代企業データへの直接適用は別問題)。
- 法人名と所在地住所の文字列正規化による同一性判定アルゴリズムを扱う日本語文献が J-GLOBAL に存在する(書誌のみ確認、本文未取得)。
- 実務で想定すべき揺れ(一般的な整理): (株)/株式会社/前株・後株、全角半角、旧字体・異体字、カナ/漢字/ローマ字、長音・中点、丁目・番地・ハイフン表記、ビル名の有無。**本節は日本語ER専用ベンチマークでの比較検証をしていない**。

## 6C. 商用MDM製品の比較と「なぜ問題を解決できなかったのか」

### 6C-0. 重要な前提(証拠の性質)
- 「製品XがY社の名寄せで失敗した」という**一次の失敗事例(契約・検証データ付き)は公開されておらず、本調査では見つけられなかった**。ベンダーは自社の失敗を公開しない。したがって以下は、(a)公開研究、(b)アナリストの要旨、(c)各社の**公式ドキュメントに書かれている設計上の前提**から導いた**推定を含む因果整理**である。製品名ごとの優劣評価はしない。
- 実際の製品選定では、候補製品について自社データでの PoC(下記)が唯一の確実な検証手段である。

### 6C-1. 確認できた事実

### 6C-2. 「なぜ解決できなかったのか」の要因分析(F1〜F6と本レポート3〜5章から導いた整理)
各要因に根拠の強さを付す。**「推定」は公開証拠が直接それを述べていないことを意味する。**

| 区分 | 要因 | 根拠 | 強さ |
|---|---|---|---|
| 組織 | 経営層の実効的コミットメントとデータオーナーシップの欠如。ガバナンス方針が守られない | F1(研究)、F2(アナリスト) | 比較的強い(ただし1研究は小規模の定性) |
| 組織 | ガバナンスが一律で現場の文脈に合わない | F2 | 要旨のみ |
| 前提の誤り | 製品がマッチする前に、**同一性の定義(粒度・時間)が合意されていない**。製品は設定された定義を実行するだけで、定義自体は決めない | F4(ルールは人が設計する)+3章 | 推定(論理的帰結) |
| 技術・設計 | マッチルールの設計・チューニングが人手依存で、専門知識と反復が要る。ルール精度ごとに自動/手動を切り分ける運用になるため、**手動レビューのキューが溢れる、または自動マージの誤統合リスクを抱える**(5章のコスト非対称性の問題) | F4、F5、F6 | 設計上の事実から推定 |
| 技術・設計 | 初回ロードや大規模処理でデータベース性能が律速となりうる | F5 | 確認(製品固有) |
| 技術・設計 | 事前学習モデル(FERN等)は汎用であり、**自社固有の属性・業務条件は別ルールで補う必要がある** | F6 | 確認(製品固有の記述) |
| 技術・設計 | **推移閉包とクラスタの誤統合**、アンマージの要件(4.4章)を製品の標準機能がどこまで保証するかは製品ごとに異なる。本調査では各製品のこの機能を検証していない | 4.4章 | 未検証 |
| 日本固有 | 住所・氏名の表記揺れ、異体字、カナなどへの対応は、製品の汎用辞書だけでは足りず、国内向けの正規化・辞書の整備が別途必要になりうる | 6B | 推定(各製品の日本語対応は未検証) |
| 連携方式 | ファイル/DB同期の遅延、削除伝播など、**連携方式の問題はMDM製品の導入だけでは消えない**(MDMは既存システムとのレジストリ型/ハブ型などの接続方式の設計が別に必要) | 2章 | 推定 |
| 契約・運用 | 製品導入後の運用(スチュワードシップ、継続的な評価・再ラベル)が予算化されない | F1(ガバナンス不遵守)に整合 | 推定 |

**結論(推定を含む)**: 商用MDM製品は、マッチ・マージ・サバイバーシップの「実行基盤」を提供するが、(1)同一性の定義、(2)誤り許容度の決定、(3)データオーナーシップ、(4)国内表記への適合、(5)連携方式の設計は、製品を買っても自動的には解決されない。公開証拠が最も強く示すのは、失敗の主因が**技術よりも組織・ガバナンス・意思決定**にあるという点であり(F1、F2)、製品固有の技術限界の証拠は、公式ドキュメント上の設計前提から推測できる範囲に留まる。

### 6C-3. 製品選定時の検証方法(第三者・再現可能)
1. **自社の実データ**からラベル付きサンプル(複数人付与)を作る。
2. 候補製品(Informatica、Reltio、Profisee、Stibo、Semarchy、Tamr など)と、OSSベースライン(Splink、Zingg)を**同じサンプル**で比較する。製品の事前学習モデルの有無、ルール設定工数も記録する。
3. 評価は、自動確定分の Precision と自動化率、クラスタ指標、スチュワードの確認工数、アンマージの可否と手順、日本語表記(株式/異体字/住所)での失敗ケースを含める。
4. 評価条件・ラベル・結果を社内監査可能な形で残す。
> 注: 本調査で公式ドキュメントを実際に確認したのは Informatica と Reltio のみ。Profisee、Stibo、Semarchy、Tamr は**未調査**である。

## 9. 本調査の限界
- 論文は要旨レベルの確認が中心で、本文の実験条件・数値の再検証はしていない。ただし古典的な部分(Accuracyの落とし穴、ブロッキング、Splinkの教師なしEM、推移閉包、日本語正規化、評価設計)は小規模PoCで、PLM・LLM・埋め込み・WDC Products・100万件規模は縮小版の実験で検証した(論文の公表値の再現ではない。PLM微調整はAbt-Buy/WDCで小予算では再現できなかった)。商用MDM製品の性能、Dittoの大規模企業データ、VLDB J. 2024のベンチマークは検証不能/未実施。詳細は [PoC-ResultAnalyticsReport.md](./PoC-ResultAnalyticsReport.md)。
- 日本語LLM性能、日本語ER専用ベンチマークは未調査。
- 法令は、PPC FAQと目次・章立ての確認が中心。条文・ガイドライン本文の逐条確認はしていない(特に番号法、利用目的の制限、共同利用の要件)。法的助言ではない。
- 商用MDMは Informatica と Reltio の公式ドキュメントの一部のみ確認。Profisee、Stibo、Semarchy、Tamr、Gartner Magic Quadrant等は未調査。各製品の日本語対応、アンマージ機能、価格・導入工数は未検証。
- 「なぜ解決できなかったか」の製品別の一次失敗事例は見つけられず、6C-2は公開研究と公式ドキュメントからの推定を含む。
- 自社データでの実測がないため、手法・製品の優劣は結論づけていない。
