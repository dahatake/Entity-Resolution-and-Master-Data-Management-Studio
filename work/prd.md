## 1. エグゼクティブサマリー

**課題**: 大企業では、業務連携を「ファイル共有」「DB同期」で行うことが多く、システムごとの採番・意味・同一性の粒度・表記が揃わない。その結果、同じ顧客・取引先・商品を同定できず、連携のたびに人手の突合や不整合が発生する [IA §2]。

**既存手段の限界**: 商用MDM製品は、マッチ・マージ・サバイバーシップの「実行基盤」を提供するが、同一性の定義、誤り許容度、データオーナーシップ、国内表記への適合、連携方式の設計は自動的には解決しない。公開証拠が最も強く示す失敗要因は、技術より**組織・ガバナンス・意思決定**である [IA §6C-2 ⚠/📄(F1,F2)]。

**プロダクトの提案**: 名寄せを「標準化 → ブロッキング → ペア判定 → クラスタリング → 統合 → 運用」のパイプラインとして分解し [IA §0(1)]、次を**一つの基盤**で提供する。

1. 日本語の法人・住所・氏名に対応した標準化(法人番号・町字IDによる外部参照を含む)
2. 決定的ルール+確率モデルのベースラインを核にした、説明可能な照合
3. **推移閉包の誤統合を防ぐクラスタリング**と、**アンマージを一級要件にしたID管理**
4. **評価ワークベンチ**(ラベル付きサンプル、信頼区間、誤統合/誤分割のコスト比による閾値決定)
5. 法令(個人情報保護法)とガバナンスを組み込んだ運用(目的・共同利用の登録、監査ログ、マイナンバーの混入防止)

**スコープの中核方針**: 「まず測る」。Phase 0 で、実データのラベル付きサンプルを使い、同一性の定義・誤りコスト・ベースラインを確定してから、機能を作る。MLモデル(PLM/LLM)は、ベースラインでは不足する領域に限って、後段で追加する [IA §6.3 ⚠、PR §11.2 ✅]。

### 2.3 商用MDM製品が問題を解決できなかった理由(要約)[IA §6C-2]
- 組織: 経営層の実効的コミットメントとデータオーナーシップの欠如、一律のガバナンス(F1/F2)。
- 前提: **同一性の定義(粒度・時間)が先に合意されていない**。製品は設定された定義を実行するだけである。
- 設計: マッチルールの設計が人手依存。自動/手動の区分により、確認キューが溢れるか、誤統合リスクを抱える(K6が定量的に裏付け ✅)。
- 日本固有: 異体字・住所・カナ表記は、汎用辞書だけでは不足しうる(⚠、各製品の日本語対応は未検証)。
- 連携: ファイル/DB同期の問題は、MDM製品の導入だけでは消えない(⚠)。
- **本PRDへの含意**: 機能で解くのは「技術」の部分であり、組織・ガバナンスの部分は**プロダクトの要求として運用機能(オーナー、承認、監査)に落とす**。製品の導入だけで解決する、という主張はしない。

## 6. 機能要求

### 6.1 取り込みと連携(FR-ING)
| ID | 要求 | 優先 | 根拠 | 受入基準(概要) |

## 8. 受入と評価の方式

### 8.1 評価の基本ルール(全フェーズ共通)
1. **自社データから**ラベル付きサンプルを作る(層化抽出、複数判定者、κを記録)。サイズの目安: 適合率の推定CI幅を±0.13以内にするには200件程度が必要(K9)。**500〜数千ペア** [IA §7]。
2. **「自動確定分の適合率」「自動化率」「クラスタ指標」「ブロッキングの再現率」を併記**し、信頼区間とサンプル数を明記する(単独のAccuracyやF1だけで判定しない)。
3. 閾値は、**業務ごとのコスト比**(誤統合1件 : 見逃し1件)から導く(PoC-04の方法)。
4. 各手法は、同一のラベル付きサンプルで比較する(ベースライン=決定的ルールとSplink型確率モデル)。

### 8.2 ベースライン(下限の目安。受入の目標値ではない)
| 項目 | PoCの値 | データ | 使い方 |
|---|---|---|---|
| 決定的ルール | 適合率1.00・再現率0.368 | fake_1000 | 自社データでの比較対象 |
| Splink型(教師なし)、ペア | 適合率1.00・再現率0.644 | fake_1000 | 同上 |
| 同、連結成分クラスタ(t=0.5) | 適合率1.00・再現率0.823 | 同上 | 同上 |
| 正規化(日本語・合成) | 再現率0.741(NFKC+法人格・住所)→0.796(+異体字)→0.953(+ファジー) | 合成11シード | 正規化の効果の確認用 |
| ブロッキング | 再現率: 単一キー30〜47%、4キー和集合81.2% | fake_1000 | 設計の目安 |
| PLM(Abt-Buy) | F1 0.894 | 公開ベンチ(全量・GPU) | ラベルが数千組ある領域での参考 |

**注意**: これらはいずれも、**デモ用・合成・公開ベンチマーク**で、自社データでは測っていない。fake_1000は誤り方が単純で、適合率が1.0になりやすい(PR §4.1)。

### 8.3 フェーズごとの出荷条件
- **Phase 0 の完了条件**: 9章の検証項目(V1〜V10)の結果が出て、Q1〜Q7(対象・定義・規模・コスト・ID継承・build/buy)と、法務の見解(V7)に決定が出ていること。
- **Phase 1 の出荷条件**: Mの要求のうち、Phase 1 に割り当てたものがすべて受入基準を満たす。特に**FR-XRF-02(アンマージ)とFR-GOV-01/03/05**。
- **Phase 2/3**: 各フェーズの要求について、評価ワークベンチで、ベースラインを上回ることを確認してから有効化する。

## 14. この文書自体の限界

- 利用者、既存システム、規模、予算、体制の情報がなく、4章のペルソナ、9章のフェーズの割当は、IA/PRの内容から導いた**仮のもの**である。
- PoCは合成データ・公開ベンチマーク・縮小版が中心で、**実データ・人間のアノテータ・商用MDMの実機評価は未実施**(PR §12.5)。商用製品の記述は、Informatica と Reltio の公式ドキュメントの一部の確認に基づく(他の製品は未調査)。
- 法令に関する記述は、PPCのFAQ・章立て・条文を引用した二次情報に基づき、**条文の逐条確認は未実施**(特に共同利用、特定個人情報)。
- アンマージ、cannot-link制約、有効期間付きの同一性、サバイバーシップは、IA/PRで**設計原則として述べられたが、PoCでは検証していない**(⚠/❓)。Phase 0(V10)で検証する。
- 数値目標を置いていない箇所は意図的である(3.3、8章)。**実データで測るまで、目標値を決めない**。
- 15章のタスクの**担当(U1〜U7)は仮置き**で、期間・工数・期限は資料に情報がないため記載していない。状態は初期値(すべて未着手)である。
- 16章の可視化は、PoCの**合成データ・公開ベンチマーク**を描いた参照プロトタイプで、実データの図ではない。約300ノードまでの描画を確認したが、それ以上の規模(NFR-12)は未検証である。
