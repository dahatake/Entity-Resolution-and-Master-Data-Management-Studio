# 09 限界と注意

本番で使う前に、必ず読んでください。**できること・できないこと・分かっていないこと**を正直に書きます。

## 位置づけ

- これは **Phase 1(ローカルで動く最初の版)** です。要求定義書(`work/prd.md`)の Phase 1 の要求 48件のうち、43件に自動テストがあり、残り5件(可視化の3件、可視化の誠実性・アクセシビリティの2件)は**ブラウザでの手動確認のみ**です(`app/docs/requirements_coverage.json`)。
- 検証は**合成データだけ**です。実データでの精度・閾値・処理時間は**未測定**です。
- **Phase 0(本番の前に決めること)は未了**です。閾値(自動0.9/下限0.5)、コスト比(5)、確認1件あたり2分、確認の期限72時間は**仮の既定値**です。同一性の定義は、業務側の承認が必要です。ダッシュボードが、この未了を警告します。

## 既知の不具合・制限

| # | 内容 | 影響と対処 |
|---|---|---|
| 1 | **「条」を含む住所が途中で切れる**(✅ 確認)。`北海道札幌市中央区北一条西9丁目27番6号` → `北海道札幌市中央区北1`。標準化の `addr` が、漢数字+「条」を数字へ変換し、最初の数字までを取って以降を落とすため | 札幌など「条・丁目」を多用する住所では、`addr` を決め手にできない。電話・法人番号など他の項目を使う。直す場合は `standardize.py` の `op_addr` |
| 2 | 異体字辞書は少数のみ登録(髙・﨑・邉…)。`齋`/`斎`、`國`/`国` は**未登録で揃わない**(✅) | 実データの値を見て辞書を足す([06](06-config-reference.md)) |
| 3 | 確率モデルの学習は、**候補ペアの中だけ**で行われる。「別」の組が候補にほとんど無い、または比較項目が2つ以下だと、学習が壊れやすい(λ が 1 や 0 に張り付く。✅) | 比較項目を3つ以上にし、ブロッキングを絞りすぎない。λ を確認する |
| 4 | 確率 p は「候補の中での確率」で、**較正されていない**。同じ 0.9 でも、データによって意味が違う | 閾値は、ラベル付きサンプルの実測(適合率・再現率)で決める。pの値そのものを信じない |
| 5 | 連結成分(既定)は、鎖でつながる別人を1つにする | エンティティ詳細で分割、または `clusterer: center`。評価の「推移閉包による影響」で確認 |
| 6 | 標準化を変えても、モデルは**自動では再学習されない** | 標準化を変えたら、「学習」→「有効化」をやり直す |
| 7 | **画面に無い操作**がある: 確認項目の担当割り当て、ラベルの裁定、既存ソースへの利用目的の紐づけ、タスクの作成、役割の変更、パスワード変更、判定の取り消し | APIで行う([07](07-operations.md))。パスワード変更・ユーザー無効化・分割の取り消しは**機能自体が無い** |
| 8 | 異なるポートで複数起動すると、同じホスト名のCookieが共有され、ログインが外れる(⚠ 観察) | `127.0.0.1` と `localhost` で使い分ける、または1つずつ使う |
| 9 | 実行は**1つずつ**。実行中にもう一度実行すると、`別の実行が進行中です` で拒否される | 終わるのを待つ |
| 10 | 確認キューの項目が多いと、画面は先頭100件だけを表示する | 閾値を調整して量を減らす。担当ごとの絞り込みはAPI |
| 11 | エンティティの詳細は、メンバーが3,000件を超えると開けない | 大きすぎるクラスタ自体が異常。閾値・ブロッキングを見直す |
| 12 | 図(つながり)は、数百ノードを超えると見づらい。閾値スライダー、橋渡しレコード・最弱リンクの強調は**未実装** | 一覧の「最低p」「下限未満の辺」で、弱いクラスタを探す |

## 規模と性能

- **純Pythonの実装**です。1,000件で名寄せ全体が約0.1秒、候補ペア2,545組(✅)。それ以上の規模での時間は**未測定**です。
- 安全装置として、候補ペアの上限(既定200万)を超える見積では、ペアを作る前に停止します。
- 数十万件以上、または候補が数百万組以上になるデータには、このまま使えない可能性が高い(⚠ 推測)。大規模には、Splink + DuckDB など別の基盤(調査・検証は `PoC/`、`work/PoC-ResultAnalyticsReport.md`)が必要です。マッチャは差し替えられる設計です(`matching.register_matcher`)。
- データは1つの SQLite ファイルです。同時に多数が使う用途は想定していません。

## 含まれないもの(Phase 2 以降)

- 事前学習言語モデル(PLM)や大規模言語モデル(LLM)による判定、kNN(文字n-gram)ブロッキング
- 法人番号・町字ID(アドレス・ベース・レジストリ)など**外部データによる付与**
- 承認ワークフロー(閾値・ルールの変更や分割に、データオーナーの承認を要求する)
- 有効期間つきの同一性(社名変更・移転・合併の履歴)、サバイバーシップ(複数ソースの値から代表値を決める)
- モニタリング(一致率の推移の警告)、ドリフトの検出
- 氏名の専用処理(姓名の分割、読み仮名、ローマ字)。人名は汎用の `name` 比較(Jaro–Winkler)のみ
- リアルタイム(オンライン)の照合。バッチ処理のみ
- 業務システムのDB/CDCへの直接接続。CSVと SQLite ファイルのみ

## セキュリティと法令

- **1台のPCで、1人〜少人数が使う前提**です。`127.0.0.1` でしか待ち受けません。HTTPS・多要素認証・パスワードの強度要件はありません。**インターネットや社内ネットワークに公開しないでください。**(別のPCから使うために、ポート転送やリバースプロキシを足すのは、想定外で未検証です。)
- DBにはレコードの**生データ**が入っています(個人データを含む場合は、そのまま)。ファイルの保護と、バックアップの管理は利用者の責任です。
- 個人番号の検出は列名とチェックデジットによる**ヒューリスティック**で、完全ではありません。取り込み前に除外してください。
- 利用目的の登録は、**確認事項の記録と実行前の統制**で、法的な適合を保証しません。個人情報保護法・番号法への対応は、法務・コンプライアンスの確認が必要です。
- 監査ログのハッシュ連鎖は、DBの全面差し替えを防げません。
