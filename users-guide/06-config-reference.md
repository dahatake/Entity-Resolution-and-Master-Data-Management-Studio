# 06 設定リファレンス

「設定」画面で入力する JSON の書き方です。**すべて `sample/` に動く例**があります([customers-std.json](sample/customers-std.json) / [customers-pipeline.json](sample/customers-pipeline.json) / [customers-model.json](sample/customers-model.json))。まずそれを貼って、少しずつ変えるのが近道です。

設定を保存すると検証され、誤りがあれば画面に理由が出ます(保存されません)。

## 1. 標準化(`標準化` カード)

比較の前に、記録を**比較用の項目**に変換します。

```json
{
 "label": "任意の名前(省略可)",
 "fields": [
  {"name": "項目名", "ops": ["操作1", "操作2"], "sources": {"*": ["元の列名", "別の列名"]}}
 ],
 "variants": {"齋": "斎"},
 "corp_forms": ["株式会社", "有限会社"]
}
```

| キー | 意味 |
|---|---|
| `fields[].name` | 比較用の項目名。**重複不可**。ブロッキングとモデルはこの名前で参照する |
| `fields[].ops` | 適用する操作。**上から順**に適用 |
| `fields[].sources` | 元の列。`"*"` はすべてのソース。ソース名を書くと、そのソースだけ別の列を使える(例: `{"*": ["name"], "crm": ["company_name"]}`)。複数の列を書くと、**空白でつないで**1つの値にする |
| `variants` | 異体字辞書(省略可)。⚠ **書くと既定の辞書が置き換わります**(既定に足したいときは、既定の内容も写す) |
| `corp_forms` | 除去する法人格の一覧(省略可)。省略すると既定(株式会社、(株)、㈱、有限会社、合同会社、医療法人…、Co., Ltd.、Inc. など) |

> 個人番号として**隔離された列**を `sources` に書くことはできません(保存が拒否されます)。

### 操作(`ops`)

| 操作 | 何をするか | 例 |
|---|---|---|
| `nfkc` | Unicode正規化。全角英数・半角カナ・㈱などを標準形に | `ＡＢＣ` → `ABC`、`㈱` → `(株)` |
| `lower` | 小文字化(大文字小文字を同一視) | `Tokyo` → `tokyo` |
| `ws` | 連続する空白を1つにして前後を削る | |
| `nospace` | 空白をすべて除く | `北斗 運輸` → `北斗運輸` |
| `punct` | 記号・句読点・空白類を除く(長音 `ー` は残す) | `(株)北斗` → `北斗` |
| `kana` | ひらがな → カタカナ | `みなと` → `ミナト` |
| `variant` | 異体字を揃える(`variants` の辞書) | `髙` → `高` |
| `corp` | 法人格を除く(前株・後株・略称とも) | `北斗運輸 株式会社` → `北斗運輸` |
| `digits` | 数字以外を除く | `03-1234-5678` → `0312345678` |
| `phone` | 数字だけにし、`+81` を `0` に直す | `+81 3-1234-5678` → `0312345678` |
| `email` | 前後の空白を削り、小文字化 | |
| `date` | `YYYY-MM-DD` に揃える(`2024/3/5`、`2024年3月5日`、`20240305`)。解釈できなければ空 | |
| `addr` | 住所: 全角→半角、漢数字→数字、丁目・番地・号→ハイフン、建物名・階数を落とす | `東京都千代田区6丁目28番15号` → `東京都千代田区6-28-15` |
| `addr_town` | `addr` の結果から**番号より前**(町字まで)を取り出す | `…丸の内6-28-15` → `…丸の内` |
| `addr_num` | `addr` の結果から**末尾の番号**を取り出す | `…丸の内6-28-15` → `6-28-15` |

組み立てのコツ:

- **法人名**: `["nfkc","lower","corp","variant","punct","nospace"]`
- **氏名(英字)**: `["nfkc","lower","ws"]`
- **電話**: `["phone"]` **/ メール**: `["email"]` **/ 生年月日**: `["date"]`
- **住所**: `["addr"]`。町字と番地を別々に比べたいなら、同じ住所列から `["addr","addr_town"]` と `["addr","addr_num"]` の2項目を作る。
- 住所を丸ごと比べる項目(`addr`)は、**ブロッキングのキー**にも使えます。

### 辞書の落とし穴

- 未登録の異体字(例: `齋`/`斎`、`國`/`国`)は**揃いません**。再現率の低下要因です。実データでは、取り込んだ値を見て辞書に足してください(✅ 検証で確認)。
- 既定の異体字: 髙→高、﨑→崎、邉・邊→辺、德→徳、廣→広、櫻→桜、濱→浜、澤→沢。
- ⚠ 住所の `addr` は「条」を数字の一部と読むため、札幌のような `北一条西9丁目` が途中で切れます(→ [09](09-limitations.md))。

## 2. ブロッキングと閾値(`ブロッキング・閾値・クラスタリング` カード)

```json
{
 "blocking": {
  "rules": [
   {"name": "ルール名", "keys": [{"field": "項目名", "t": "exact"}]}
  ],
  "max_block": 500,
  "max_candidates": 2000000,
  "link_type": "all"
 },
 "thresholds": {"auto": 0.9, "review_low": 0.5},
 "clusterer": "components",
 "seed": 1
}
```

| キー | 意味 |
|---|---|
| `rules[].name` | ルール名。**重複・空は不可** |
| `rules[].keys` | キーの並び。**すべて同じ**組が候補になる(AND)。複数のルールは**和集合**(OR) |
| `keys[].field` | 標準化で作った項目名 |
| `keys[].t` | 変換: `exact`(既定。完全一致)/ `prefix`(先頭 `n` 文字)/ `suffix`(末尾 `n` 文字)/ `year`(日付の年)/ `ym`(日付の年月)。`prefix`・`suffix` は `n` が必須 |
| 空の値 | キーのどれかが空の記録は、**そのルールでは候補にならない** |
| `max_block` | 1つのブロック(同じキーの記録の集まり)の最大件数。**超えたブロックは丸ごと無視**する(「株式会社」のような巨大ブロック対策)。見積で「除外ブロック」に出る |
| `max_candidates` | 候補ペアの上限。見積が超えると、ペアを作る前に実行が止まる |
| `link_type` | `all`(全記録同士)/ `cross`(**別のソース同士だけ**を比べる。ソース内の重複は探さない) |
| `thresholds.auto` | これ以上の確率は自動マージ |
| `thresholds.review_low` | これ以上 `auto` 未満は確認キュー。これ未満は却下。**0 ≤ review_low ≤ auto ≤ 1** |
| `clusterer` | `components`(連結成分。既定)/ `center`(中心法。連鎖による過剰統合を抑える) |
| `seed` | 乱数の種(再現性のため記録される) |

ブロッキングの設計の目安:

1. まず、**決め手になる項目**(電話、メール、法人番号、生年月日など)を1ルールずつ。
2. 表記ゆれに弱いキーだけだと取りこぼすので、**複数のルールを足す**(和集合)。
3. **絞りすぎない**。「別」の組が候補にほとんど入らないと、モデルが学習できず壊れます(→ [04](04-your-own-data.md))。
4. 正解のあるデータなら、評価画面の「ブロッキングのルール別寄与」と PC で、効くルールと効かないルールを見分ける。

## 3. モデル(`モデル` カード)

### 確率モデル(Fellegi–Sunter): `"matcher": "fs"`

```json
{
 "matcher": "fs",
 "fields": [
  {"name": "name", "cmp": "text"},
  {"name": "tel", "cmp": "exact"}
 ]
}
```

各項目を**比較関数**で比べ、一致の水準(段階)ごとの証拠を合算して確率にします。水準ごとの m(同一のときに出る確率)と u(別のときに出る確率)は、**候補ペアから自動で学習**されます(「学習」ボタン)。空の項目は「欠損(比較しない)」で、確率に影響しません。

| 比較関数 `cmp` | 水準(上ほど似ている) | 向いている項目 |
|---|---|---|
| `exact` | 完全一致 / 不一致 | 電話、番地、コード、都道府県 |
| `name` | 完全一致 / JW≥0.92 / JW≥0.85 / 不一致 | 人名・短い名前 |
| `text` | 完全一致 / JW≥0.95 / JW≥0.88 / JW≥0.75 / 不一致 | 法人名、町字など長めの文字列 |
| `addr` | 完全一致 / 同一街区(末尾の番号違い)/ 同一町字(番地違い)/ JW≥0.9 / 不一致 | 標準化した住所全体 |
| `date` | 完全一致 / 1文字差・入替 / 同年月 / 同年 / 不一致 | 生年月日 |
| `email` | 完全一致 / ローカル部一致 / JW≥0.9 / 不一致 | メール |

「JW」は Jaro–Winkler 類似度(0〜1。1に近いほど似ている)です。

任意のキー(省略可): `prior_count`(平滑化の事前カウント。既定 0.5)、`monotone`(「似ているほど一致の証拠が強い」という単調性を課す。既定 `true`)。

### 決定的ルール: `"matcher": "deterministic"`

信頼できるキー(法人番号など)が**同じなら同一**とする方式です。学習は不要です。

```json
{
 "matcher": "deterministic",
 "rules": [
  {"name": "法人番号が同じ", "fields": ["corp_no"], "p": 0.999}
 ]
}
```

`p` は、そのルールに一致したときの確率(0 より大きく 1 以下)。

### ハイブリッド: `"matcher": "hybrid"`

`fields`(確率モデル)と `rules`(決定的ルール)の両方を書きます。**ルールに一致したら、その `p` を下限として採用**し、一致しなければ確率モデルの値を使います。既存のキー(旧システムのID)を「証拠の1つ」として使うときに向きます。

```json
{
 "matcher": "hybrid",
 "fields": [{"name": "name", "cmp": "text"}, {"name": "tel", "cmp": "exact"}],
 "rules": [{"name": "法人番号が同じ", "fields": ["corp_no"], "p": 0.999}]
}
```

> ルール(`rules`)の `fields` は、**標準化で作った項目名**で、両方が空でなく同じ値のときに一致とみなします。

### 学習結果の読み方

「学習」後、モデル表に「済(λ=0.183)」と出ます。

- **λ が 1.000 や 0.000 に近い**: 学習が壊れています。ブロッキングが絞りすぎ(または緩すぎ)ないか見直す。
- 確認画面の根拠では、項目ごとに `log2(m/u)`(ビット)を出します。**正=一致の証拠、負=不一致の証拠**。
- 確率 p は、**候補ペアの中での確率**です。全体の確率ではありません。閾値は、ラベルを付けた実測で決め直してください。

## 4. 変更の履歴と再現性

- 標準化は版(ハッシュ)で管理され、**同じ内容は同じ版**です。有効な版は、いつでも切り替えられます。
- 実行には、標準化の版・モデル(設定+学習結果のハッシュ)・乱数の種が記録されます。
- 変更はすべて監査ログに残ります。
